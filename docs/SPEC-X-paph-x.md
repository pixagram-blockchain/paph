# PAPH-X — Specification
## Retrieval-native perceptual comparison with sub-quadratic screening

**Status:** Proposed engineering specification  
**Predecessor:** PAPH 4.2.3 / Comparator 42  
**Primary objective:** reduce screening cost and pairwise hash-comparison cost by **10× or more** on the target search workload while preserving PAPH's copy-detection recall and calibrated decision semantics.  
**Design principle:** do not optimize the 512×512 matcher harder; make it unnecessary for most pairs.

---

## 0. Executive decision

PAPH 4.2.3 is already heavily optimized internally, but its comparison architecture remains dominated by a structural problem:

```text
current
query ──► full 512×512 descriptor scan ──► Lowe/mutual-best ──► Hough ──► channels ──► lattice
                 262,144 pair distances
```

PAPH-X replaces this with an evidence cascade:

```text
PAPH-X
query ──► XRoute batch screen ──► sparse descriptor retrieval ──► adaptive geometry
              ~100-byte route            ~O(N·K) candidates          96 → 512 keypoints
                    │                           │                         │
                    └──────────────► lazy structural evidence ◄──────────┘
                                                │
                                      fast decision / fallback
```

The important architectural changes are:

1. **A pair is screened from a compact route signature, not from descriptors.**
2. **Descriptor matching becomes sparse via multi-projection LSH.**
3. **Only 96–128 anchor keypoints are used initially; the full 512 are expanded adaptively.**
4. **Screening never constructs or sorts a correspondence vector merely to count it.**
5. **Structural channels are evaluated lazily, in cost-to-discrimination order.**
6. **Direct and mirror hypotheses share the same retrieval pass; mirroring is a descriptor/geometry transform, not another complete scan.**
7. **All temporary arrays are fixed-capacity scratch buffers; hot paths do not allocate.**
8. **The old exhaustive matcher remains available as a fallback/audit path.**
9. **Ranking is batch-oriented: the query is SIMD-compared against many candidate route signatures at once.**

The target is not a 10× microbenchmark on one inner loop. The release gate is a **10× or greater end-to-end reduction in screening and pairwise comparison cost for the search workload**, with a separately reported positive-copy latency.

---

# 1. Scope

PAPH-X is the next-generation **comparison and retrieval layer** built on the deterministic PAPH fingerprint generated by 4.2.x.

The 4.2 wire remains the evidence source during the first implementation. PAPH-X does **not** require re-hashing the image corpus merely to obtain the accelerator structures.

PAPH-X defines three related products:

- **XRoute** — an extremely small pair-screening signature.
- **XMatch** — a sparse descriptor matcher and geometric verifier.
- **XRank** — a batch search path that applies XRoute to many candidates before invoking XMatch.

The original PAPH 4.2 comparator remains the normative fallback/audit implementation until PAPH-X calibration is proven on the production corpus.

---

# 2. Observed PAPH 4.2 bottlenecks

PAPH 4.2.3 already contains several excellent optimizations: packed `u64` descriptors, SIMD FAST-9, shared scans, lazy Hungarian assignment, fixed vote tables, scratch reuse, and a one-call `rank42` ABI.

PAPH-X therefore attacks the remaining architectural costs rather than reproducing them with slightly faster arithmetic.

## 2.1 Screening still performs the expensive matcher

The current stage-1 screen invokes the same correspondence constructor used by geometry and asks only for its length.

Conceptually:

```rust
let pd = corr_42(ctx.direct(), &ca.kp, &cb.kp, profile).len();
let pm = corr_42(ctx.mirror(), &ca.kp, &cb.kp, profile).len();
```

The current correspondence constructor still:

- allocates best/second-best arrays;
- computes the complete pairwise descriptor matrix;
- constructs `Corr42` records;
- sorts the result.

The screen needs none of the sorted correspondence order.

This is the first PAPH-X rule:

> **A screen must never build evidence that its caller immediately throws away.**

## 2.2 The descriptor problem is still O(N²)

At 512 keypoints:

```text
512 × 512 = 262,144 descriptor pairs per hypothesis
```

With a direct and mirror hypothesis, the descriptor stage is effectively doubled.

The current Rust implementation is fast because each pair uses four `POPCNT`s, but the asymptotic shape remains quadratic.

PAPH-X changes the problem from:

```text
all A × all B
```

to:

```text
A × a very small descriptor candidate set generated by LSH
```

The exhaustive matcher becomes a fallback, not the default path.

## 2.3 Ranking is still pair-oriented

`rank42` already removes language/ABI overhead, but the engine still visits candidates one by one.

The query is fixed while candidate route data varies, which is ideal for SIMD across candidates.

PAPH-X therefore makes XRank a first-class batch operation rather than a loop around a pair comparator.

## 2.4 The decision path evaluates more evidence than it usually needs

The 4.2 lean comparator still computes substantial structural and geometric evidence before the final lattice decides.

PAPH-X introduces an explicit **lazy evidence scheduler**:

```text
cheap high-rejection evidence
          ↓
cheap structural evidence
          ↓
sparse geometry
          ↓
expensive corroboration
          ↓
full legacy audit only if ambiguity remains
```

A channel that cannot change the verdict must not be evaluated.

# 3. Design goals

## 3.1 Performance goals

On the current target class of machine used by the 4.2 benchmarks (single x86-64 core, WebAssembly SIMD128 or native SIMD/POPCNT), the initial release budget is:

| Operation | PAPH 4.2.3 reference point | PAPH-X target |
|---|---:|---:|
| pair screen | ~1.0–1.5 ms | **≤ 0.10 ms p50, ≤ 0.20 ms p95** |
| unrelated pair, lean compare | ~4.2 ms WASM SIMD | **≤ 0.40 ms p50, ≤ 0.80 ms p95** |
| positive copy, fast path | ~4–6 ms WASM SIMD | **≤ 0.50 ms p50, ≤ 1.00 ms p95** |
| 100-candidate batch screen | ~100–150 ms class | **≤ 10–15 ms** |
| 100-candidate rank with ≤10 survivors | ~screen + full comparisons | **≥10× faster end-to-end** |

These are **release targets**, not measured PAPH-X results.

The 10× claim is valid only after the benchmark suite demonstrates it.

## 3.2 Accuracy goals

PAPH-X must be evaluated against the same transform and attack families as PAPH 4.2 plus a larger real moderation corpus.

Release gates:

- `Identical` exactness: 100%.
- Golden copy recall through XRoute/XMatch: 100% on the normative transform corpus.
- Screen recall on normative copies: 100%.
- Production copy recall: target ≥99.5% before fallback; ≥99.9% after fallback.
- Precision at the chosen `Copy` operating point: no worse than 4.2 on the calibration corpus.
- Symmetry: `compare(A,B)` and `compare(B,A)` remain identical modulo explicitly directional fields.
- Mirroring: direct and mirrored hypotheses remain semantically equivalent under the same transform.
- Determinism: identical input wires yield identical XRoute, XMatch and XRank records across Rust and WebAssembly builds.

The final comparator is allowed to return `Indeterminate`/`FallbackRequired` rather than silently inventing evidence.

# 4. PAPH-X architecture

PAPH-X is a six-stage cascade.

```text
Stage X0   Identity / validity
   │
Stage X1   XRoute batch screen
   │
   ├── reject / unscreened
   │
   └── candidate survives
            │
Stage X2   Sparse descriptor retrieval
            │
Stage X3   Adaptive geometric verification
            │
Stage X4   Lazy structural corroboration
            │
Stage X5   Fallback / audit comparator when ambiguity remains
```

The ordering is deliberate: the cheapest stage with useful rejection power runs first.

---

# 5. X0 — exact identity and validity

Before any perceptual operation:

1. Validate both Tier-1 wires.
2. Validate Tier-2 headers when supplied.
3. Check comparator/hash profile compatibility.
4. Compare the complete canonical Tier-1 fingerprint bytes.
5. If the fingerprint is byte-identical, return `Identical` immediately.

No descriptor structures are built for an exact-identical pair.

This must remain an exact test, not a perceptual shortcut.

---

# 6. X1 — XRoute

XRoute is the new primary screening primitive.

It is derived from already-existing PAPH 4.2 data. It is not a cryptographic digest and must never be confused with one.

## 6.1 XRoute contents

Recommended logical structure:

```text
XRoute
├── version/profile id
├── global[4]              256-bit coarse invariant signature
├── local_minhash[64]      64 × u8 b-bit MinHash
├── band_minhash[32]       32 × u8 b-bit MinHash
├── local_count            u16
├── descriptor_count       u16
├── geometry_class         u16
└── flags                  u16
```

Target packed size: **≤128 bytes** per side.

The route can be stored as a sidecar or generated at `prepare()` time. It should not become mandatory consensus wire data in the first PAPH-X release.

## 6.2 Local MinHash family

The input set is the existing canonical Tier-1 local-code family.

For each side:

1. obtain the canonical local codes;
2. remove duplicates;
3. apply deterministic 64-bit mixing with 64 fixed salts;
4. retain the low 8 bits of the minimum hash per lane.

The function is deterministic and profile-versioned.

The 8-bit form is intentionally used for screening only. False positives are harmless because XRoute never certifies a copy by itself.

The exact local-code set remains available for XRoute refinement and final evidence.

## 6.3 Descriptor-band MinHash family

Use the same descriptor-band concept already exposed by `indexKeys()`.

Each keypoint descriptor contributes the existing 24-bit bands. For screening, the set of bands is MinHashed into 32 lanes.

For the route version used for search, both direct and mirror-compatible band families should be represented.

This allows a mirrored or cropped copy to produce a strong route even when the geometric matcher has not run yet.

## 6.4 Global invariant signature

The four 64-bit words are derived from coarse, existing Tier-1 evidence:

- low-resolution shape/silhouette structure;
- run-length distribution;
- coarse palette/brightness-independent structure;
- coarse DCT/energy layout.

These are **not** a simple cryptographic hash of the bytes.

Recommended construction:

```text
G0 = canonical 4×4 occupancy / edge class signature
G1 = canonical run-length class signature
G2 = palette-independent luminance topology signature
G3 = coarse frequency/energy class signature
```

Each is canonicalized under the transformations that PAPH-X intends to survive.

The global signature is primarily a rejection signal.

## 6.5 XRoute similarity

A route similarity has three independent readings:

```text
Rlocal  = equal(local_minhash lanes) / 64
Rband   = equal(band_minhash lanes)  / 32
Rglobal = similarity(global signatures)
```

PAPH-X must **not** collapse these into an undifferentiated confidence number for final decisions.

The screen is rule-based:

```text
PASS_FAST when:
    Rlocal >= T_local_fast
 OR Rband  >= T_band_fast
 OR Rglobal >= T_global_fast

DEFER when:
    one route family is moderately positive
    but no fast-path certificate exists

REJECT when:
    all route families are below their calibrated lower bars
```

`DEFER` is critical. It prevents a cheap screen from becoming an accidental recall gate.

# 7. XRank — batch screening across candidates

Search workloads must not screen candidates pair by pair.

The query route is packed into SIMD-friendly registers and candidate routes are stored column-major:

```text
candidate-major objects are forbidden in the hot screening loop

prefer:

localMH[ lane ][ candidate ]
bandMH [ lane ][ candidate ]
global [ word ][ candidate ]
```

For WASM SIMD128, process 16 `u8` or 8 `u16` candidate lanes at a time.

A 64-lane MinHash comparison therefore becomes a small number of vector compares and population-count reductions rather than 100 independent function calls.

## 7.1 XRank output

For each candidate:

```text
state:
  -1  rejected / unscreened
   0  candidate for XMatch
   1  deferred to exact fallback

route_local
route_band
route_global
route_class
screen_reason
```

The output buffer is an SoA `Int32Array`/Rust slice, not a heap-allocated object per candidate.

## 7.2 Search interaction

The existing inverted index remains useful.

The recommended search pipeline becomes:

```text
index postings
      ↓
cheap nomination
      ↓
XRank batch route screen
      ↓
XMatch on the few survivors
      ↓
legacy fallback only for DEFER / ambiguity
```

This means the expensive comparator is no longer asked to perform retrieval work.

# 8. X2 — sparse descriptor retrieval

This is the central replacement for the quadratic descriptor matrix.

## 8.1 Descriptor representation

Keep the 32-byte PAPH descriptor semantics.

For matching, store descriptors in an aligned representation:

```rust
struct DescX {
    q: [u64; 4]
}
```

No mirrored descriptor array is stored.

The mirror operation is represented by a fixed word/byte mapping and performed at load time.

This removes the duplicate 32-byte descriptor storage currently held for the mirrored side.

## 8.2 Stable projection family

For every 256-bit descriptor, define a fixed profile-owned family of **24 8-bit projections**.

Each projection selects 8 descriptor bits according to a published deterministic permutation table:

```text
projection 0 → bit positions P[0..7]
projection 1 → bit positions P[8..15]
...
projection 23 → bit positions P[184..191]
```

The projection positions are selected once from real transform data to maximize:

- repeatability under scaling;
- repeatability under recolouring;
- repeatability under nearest-neighbour resampling;
- entropy across unrelated art;
- mirror consistency.

The table is part of the PAPH-X profile, not an implementation detail.

A second fixed mapping describes the mirrored descriptor.

## 8.3 Per-side XBucket index

Each prepared side builds a compact CSR-style bucket index:

```text
projection 0..23
    each has 256 byte-value buckets
        bucket → contiguous keypoint ids
```

Logical structure:

```rust
struct XBucketIndex {
    offsets: [u16; 24 * 257],
    ids:     Vec<u16>,
}
```

With ≤512 keypoints:

```text
24 × 512 ids × 2 bytes = 24 KiB
24 × 257 offsets × 2  ≈ 12 KiB
```

The exact in-memory representation may be compressed, but it must remain allocation-free during query matching.

The index is derived data. It does not need to be part of the consensus fingerprint wire.

## 8.4 Sparse candidate generation

For each query descriptor:

```text
for projection p in selected projections:
    code = project(query_desc, p)
    visit bucket[p][code]
    mark candidate keypoint ids
```

A fixed-capacity stamp array replaces hash sets:

```text
seen_stamp[512]
collision_count[512]
```

Each candidate keypoint is visited at most once per projection and deduplicated by its stamp.

Only candidates touched by the projection index are eligible for exact Hamming evaluation.

## 8.5 Collision threshold

The first retrieval pass uses a **one-collision recall-biased rule**:

```text
candidate if at least one projection matches exactly
```

A second micro-score may raise the exact-comparison threshold when buckets are unusually hot:

```text
micro_support = number of equal projections
```

Recommended behaviour:

```text
normal buckets:          support >= 1
high-frequency buckets:  support >= 2
very strong keypoints:   support >= 1
```

A bucket is considered high-frequency when its posting count crosses a profile-defined cap.

Constant or low-information projection buckets are ignored.

## 8.6 Expected complexity

For unrelated descriptors, a random 8-bit projection has an expected collision frequency near 1/256 per candidate.

With 24 projections and 512 candidate descriptors, the raw touched set is typically in the tens of candidates rather than 512.

The expected hot path becomes approximately:

```text
512 query descriptors
× 24 tiny bucket probes
+ exact Hamming on a small candidate set
```

rather than:

```text
512 × 512 full Hamming distances
```

The exact candidate count must be measured on the production corpus; the above is an architectural expectation, not a benchmark claim.

## 8.7 Sparse mutual-best matcher

The sparse matcher reproduces the conceptual semantics of 4.2:

- best distance;
- second-best distance;
- mutual best;
- Lowe ratio;
- absolute margin;
- Hamming ceiling;
- confidence;
- strength compatibility.

However it never constructs distances for candidate pairs that LSH did not nominate.

Data structures are fixed-capacity arrays:

```text
A.best[512]
A.d1[512]
A.d2[512]
B.best[512]
B.d1[512]
B.d2[512]
```

These live in reusable thread-local scratch.

## 8.8 Exactness fallback

LSH is a retrieval accelerator, not a proof that a pair does not match.

PAPH-X therefore has three outcomes from X2:

```text
SPARSE_CONFIDENT
SPARSE_AMBIGUOUS
SPARSE_INSUFFICIENT
```

`SPARSE_CONFIDENT` proceeds to X3.

`SPARSE_AMBIGUOUS` may proceed to X3 if route evidence is strong.

`SPARSE_INSUFFICIENT` triggers the exact PAPH-X fallback matcher or the legacy 4.2 matcher according to configuration.

This is the mechanism that prevents the speed optimization from silently becoming a recall regression.

# 9. X3 — adaptive geometric verification

The current geometry pipeline already has a good Hough → fit → refit → inlier structure.

PAPH-X keeps that model family but changes **how many correspondences it needs before paying for it**.

## 9.1 Anchor tier

Define a small deterministic anchor subset:

```text
XAnchor = min(96, keypoint_count)
```

Anchors are selected from the same quality/diversity principles already established in 4.2:

1. strength;
2. spatial spread;
3. scale diversity;
4. descriptor novelty.

The anchor order is deterministic and stored/derivable.

## 9.2 Anchor geometry

The first geometric model uses only XAnchor correspondences.

The objective is not final evidence yet. It is to answer:

```text
Is there an obvious coherent transformation?
```

The anchor model uses:

- translation bins;
- quantized scale;
- 64-sector rotation;
- direct/mirror hypothesis;
- confidence-weighted vote mass.

The existing bounded vote table is retained.

## 9.3 Adaptive expansion

If the anchor model is strong:

```text
96 → stop
```

or

```text
96 → 160
```

If the model is plausible but under-supported:

```text
96 → 256 → 512
```

Only the expansion needed to cross the confidence gate is performed.

This is the second major PAPH-X complexity reduction.

## 9.4 Model certificate

A fast geometric certificate requires:

```text
minimum unique A support
minimum unique B support
minimum confidence sum
minimum spatial spread
bounded residual
transform stability between anchor and expanded sets
```

A model that consists of ten adjacent points on one texture patch must not certify a copy.

The 4.2 diversity and topology controls remain conceptually applicable.

## 9.5 Mirror in one retrieval pass

Do not run:

```text
direct full retrieval
mirror full retrieval
```

Instead derive both query projection codes from the same descriptor load:

```text
projection(code_direct)
projection(code_mirror)
```

The candidate bucket index is reused.

The only additional cost is projection/shuffle arithmetic and mirror-specific geometry coordinates.

# 10. X4 — lazy structural evidence

PAPH-X keeps the multi-channel philosophy but stops evaluating channels that cannot change the outcome.

## 10.1 Evidence scheduling

Recommended order by discrimination-per-nanosecond:

```text
1. route local / bands
2. exact local-code overlap
3. coarse shape / silhouette
4. geometry certificate
5. runs / topology
6. DCT
7. palette
8. expensive local assignment / full 4.2 channels
```

The order may be calibrated but must be profile-defined.

## 10.2 Early rejection

Suppose the current partial structural evidence cannot reach the calibrated `Related` threshold even if all remaining channels score zero-to-maximum within the lattice rules.

Then stop.

More generally, each scheduler step computes:

```text
lower_bound(final_state)
upper_bound(final_state)
```

from the measurable evidence and the known ranges of the remaining channels.

If both bounds map to the same outcome, return immediately.

## 10.3 Early certification

Likewise, if a combination of:

- strong XRoute support;
- strong geometric model;
- sufficient independent spatial coverage;
- adequate descriptor uniqueness;

already satisfies the calibrated Copy rule, no additional weak channels are required unless the profile explicitly requires corroboration.

## 10.4 No averaged structural/geometric axis

PAPH-X preserves a strict distinction:

```text
STRUCTURAL evidence
GEOMETRIC evidence
```

They are not averaged into one score.

Each axis can terminate independently and the verdict lattice combines them through explicit rules.

This preserves the key safety property established in PAPH 4.x: a giant score on one axis must not drag a silent other axis over the certification boundary.

---

# 11. X5 — fallback and audit

The exhaustive path is retained under an explicit name:

```text
EXACT42
```

It is not the default search path.

Fallback is invoked when:

- XRoute is ambiguous;
- sparse descriptor coverage is too low;
- the anchor model is unstable;
- spatial diversity is insufficient;
- a structural-only Copy would otherwise be borderline;
- profile policy is `strict`;
- an operator requests audit mode.

The fallback may call the existing PAPH 4.2 comparator unchanged for the initial implementation.

Later, its descriptor scan can be replaced by an exhaustive PAPH-X kernel while retaining the same semantics.

# 12. Screening algorithm

## 12.1 Pair screen pseudocode

```text
screen_x(query, candidate):

    X0 validate + exact identity
        if identical → IDENTICAL

    X1 route comparison
        rlocal, rband, rglobal

        if route hard-negative → REJECT
        if route fast-positive → continue
        if route ambiguous     → DEFER

    X2 anchor sparse retrieval
        direct + mirror
        build sparse mutual-best pools

        if neither pool can reach geometry floor:
            if route is definitively weak → REJECT
            else → DEFER / fallback

    X3 anchor geometry
        find best direct/mirror model

        if strong coherent model:
            FAST
        else if ambiguous:
            DEFER
        else:
            REJECT
```

The screen returns **why** it rejected/deferred, not just a boolean.

## 12.2 Screening contract

`REJECT` means:

> PAPH-X has enough calibrated evidence that spending the expensive comparator budget on this candidate is not justified under the configured operating point.

`DEFER` means:

> the cheap stages did not prove the candidate, but they also did not safely eliminate it.

This distinction is mandatory.

---

# 13. Pair-comparison algorithm

```text
compare_x(A, B):

    X0 identity

    X1 route
        ├─ weak → cheap structural path
        └─ non-weak → sparse geometry path

    X2 sparse descriptor retrieval

    X3 anchor model
        ├─ strong → evidence certificate
        └─ weak → expand to 160/256/512

    X4 lazy structural channels

    lattice

    if ambiguous or fallback required:
        EXACT42
```

The fast path should normally touch only one or two expensive structures.

---

# 14. Batch ranking algorithm

XRank is a distinct optimized execution path.

## 14.1 Stage A — route SIMD

Given one query and N candidates:

```text
query route
      ↓
SIMD compare against candidate SoA
      ↓
bitset of survivors
```

The output is a compact candidate bitset.

## 14.2 Stage B — candidate-side descriptor indices

Only route survivors enter descriptor retrieval.

For a typical workload, the candidate count should drop before any descriptor Hamming calculation.

## 14.3 Stage C — positive survivors

Only candidates with a sparse geometric or strong structural signal enter full XCompare.

## 14.4 No per-candidate allocations

The rank API must reuse:

```text
route scratch
bucket scratch
match scratch
geometry scratch
output records
```

for the whole batch.

# 15. Data layout and memory rules

PAPH-X is intended to be SIMD-first.

## 15.1 Keypoint SoA

The hot geometry state should use:

```text
x[]       u16
 y[]      u16
level[]   u8
sector[]  u8
strength[] u16
```

Coordinates are already bounded by the 16-bit PAPH frame, so `i32` is unnecessary in the hot representation.

The public/semantic representation may remain wider if required for compatibility; the prepared accelerator representation should not.

## 15.2 Descriptor layout

Use aligned `[u64;4]` descriptors.

Do not store `desc_m` as a second full vector.

A mirror is a register permutation.

## 15.3 Scratch

All hot arrays are fixed-capacity to the current maximum of 512 keypoints.

At minimum:

```text
bestA[512]       u16
bestB[512]       u16
d1A[512]         u16
d2A[512]         u16
d1B[512]         u16
d2B[512]         u16
stamp[512]       u16
support[512]     u8
candidate_ids[]  u16
corr[]           fixed / bounded
```

No `Vec::push` occurs in the screen loop.

## 15.4 Candidate lists

All candidate lists have a hard capacity.

If a bucket exceeds the profile hot-bucket threshold, it is classified as low-information and is not allowed to dominate the sparse matcher.

# 16. SIMD requirements

## 16.1 WASM SIMD128

The WASM target must support:

- vector equality for XRoute MinHash lanes;
- packed integer accumulations;
- byte/word shuffle for descriptor projections;
- explicit Hamming reduction kernels;
- vectorized candidate scoring;
- branch-minimized bucket traversal.

Do not rely on LLVM automatically choosing the ideal implementation for every popcount loop.

The 4.2 experience already demonstrated that the wrong automatic vectorization strategy can make an apparently SIMD-friendly popcount slower.

## 16.2 Native

Native builds should select the best available kernel:

```text
AVX2 / AVX-512 when available
SSE2 fallback
POPCNT fallback
scalar reference
```

The reference semantics must remain identical.

## 16.3 SIMD across candidates

For XRank, SIMD should operate primarily across candidate signatures rather than repeatedly across one candidate pair.

This is the natural vectorization axis because the query stays constant.

---

# 17. Hashing changes

PAPH-X does not require a new image hash in version 1.

The existing 4.2 Tier-1/Tier-2 fingerprint remains the source of truth.

Optional hash-time additions:

- persist XRoute if it is generated during hashing;
- persist the XAnchor order;
- persist the 24 projection codes per keypoint in an off-chain accelerator cache.

These additions must never alter the canonical 4.2 wire unless PAPH-X later introduces an explicitly new fingerprint wire.

This makes the migration practical for an existing corpus.

---

# 18. Optional PAPH-X accelerator sidecar

For high-volume servers, define an optional binary sidecar:

```text
magic       4 bytes   "PAX1"
version     u16
flags       u16
profile_id  32 bytes
route       ≤128 bytes
anchor map  bounded
projection tables / CSR buckets
CRC         u32
```

The sidecar is content-derived from the PAPH wire.

It is therefore safe to cache, discard, recompute or regenerate when the profile changes.

The sidecar is not consensus state.

# 19. Index integration

The existing PAPH 4.2 exact-key index remains useful:

```text
local code postings
24-bit descriptor band postings
```

PAPH-X adds a second level instead of replacing it:

```text
Level 0: exact postings nomination
Level 1: XRoute batch screen
Level 2: sparse descriptor XMatch
Level 3: exact fallback
```

The index should continue to use exact integer keys. Fuzzy logic belongs inside XRoute/XMatch, where it is versioned and calibrated.

## 19.1 Candidate budgeting

Recommended default budgets:

```text
index nomination            K = 32 per family
union nomination            ≤64–96
XRank route survivors       ≤32
XMatch full evaluations     ≤8–16
EXACT42 fallback            only DEFER / audit cases
```

These values are starting points for calibration, not immutable constants.

# 20. Calibration profile X1

PAPH-X requires its own profile version.

At minimum it must contain:

```text
route thresholds
MinHash lane counts
projection permutation id
hot-bucket cap
anchor count
anchor expansion schedule
LSH support thresholds
Hamming ceiling
Lowe ratio
Lowe margin
geometry minimum
coverage floor
structural early-exit bounds
fallback policy
```

Profile identity must include every parameter that can affect an XRoute or XMatch result.

Two nodes using different projection tables or anchor policies must never claim to have produced the same PAPH-X result.

# 21. Verdict semantics

The existing PAPH classes remain:

```text
Identical
Copy
Suspected
Related
Unrelated
Indeterminate
```

PAPH-X additionally exposes an execution state:

```text
FAST
DEFERRED
FALLBACK
AUDIT
```

Execution state is not part of the semantic verdict.

For example:

```text
verdict = Copy
execution = FAST
```

or

```text
verdict = Copy
execution = FALLBACK
```

Both mean Copy; the latter says the fast accelerator did not have enough evidence to certify efficiently.

# 22. Symmetry and determinism

PAPH-X must preserve the existing canonical ordering rule:

```text
canonical(A,B) = lexicographically smaller Tier-1 side first
```

All directional state is computed in canonical order and mapped back at the report boundary.

The following must be symmetric:

```text
route score
screen class
verdict
structural evidence
geometric evidence
fallback decision
```

The following may be directional and must be explicitly documented:

```text
reported correspondence indices
reported dx/dy
reported transform direction
```

The equivalence discipline from PAPH 4.x should be extended to:

- XRoute bytes;
- XBucket derived contents;
- sparse candidate sets;
- anchor order;
- XMatch verdicts;
- XRank records;
- fallback decisions.

---

# 23. Correctness model for the LSH fast path

PAPH-X must not treat LSH as a proof of non-similarity.

The correctness strategy is therefore layered.

## 23.1 Positive preservation

A known copy should produce:

```text
route support
    ↓
sparse correspondences
    ↓
coherent model
```

with sufficient margin.

## 23.2 Ambiguity preservation

When that chain fails to be convincing, the engine must return `DEFER` rather than assume `Unrelated`.

## 23.3 Exhaustive fallback

`DEFER` invokes the exact comparator path when configured for high recall.

Thus the optimization is allowed to be **incomplete as a retrieval accelerator**, but not silently overconfident.

This distinction is essential.

---

# 24. Exact screen shortcut

A dedicated function must replace the current `corr_42(...).len()` screen pattern:

```rust
fn screen_count_x(..., limit: usize) -> ScreenCount
```

It must:

- never allocate a correspondence vector;
- never sort;
- stop once `limit` is reached;
- share descriptor candidate retrieval between direct and mirror hypotheses;
- reuse thread-local scratch;
- return coverage diagnostics.

Recommended result:

```text
count_direct
count_mirror
coverage_direct
coverage_mirror
support_direct
support_mirror
state
```

The caller can then distinguish:

```text
zero evidence
thin evidence
sufficient evidence
```

without constructing geometry objects.

---

# 25. Exact Hamming kernel

The existing four-`u64` Hamming implementation remains the exact reference.

PAPH-X adds a sparse-batch kernel:

```text
hamming_many(query_desc, candidate_ids)
```

where candidate IDs come from the XBucket retrieval set.

The kernel should:

1. load candidate descriptors contiguously where possible;
2. XOR four words;
3. POPCNT each word;
4. accumulate into `u16`;
5. update best/second-best without branches when beneficial;
6. avoid writing full distance matrices.

The output is only:

```text
best
second-best
argmin
```

There is no `N×M` distance matrix in memory.

---

# 26. Geometry optimization after sparse matching

The geometry stage must consume the correspondence list directly.

The following allocations from the old path should remain eliminated:

```text
per-correspondence vote Vec
HashMap per verification
repeated mask allocation
repeated residual allocation
full duplicated mirrored descriptor storage
```

The 4.2 fixed vote table and scratch architecture are retained and extended.

The main additional optimization is that the vote table is now fed by a much smaller, higher-quality correspondence pool.

---

# 27. Structural fast path

PAPH-X needs a path for copies where geometry is not the strongest evidence, especially recolours or structurally identical recompositions.

Recommended structural fast path:

```text
exact local-code intersection
        +
XRoute local MinHash
        +
coarse shape/silhouette agreement
        +
coverage
```

A structural-only Copy requires spatial support and multiple independent families.

A repeated tile wall must remain prevented from certifying simply because the same texture occurs many times.

The current PAPH 4.2 repetition and corroboration ideas therefore remain policy constraints.

---

# 28. Lazy verdict lattice

PAPH-X should expose a scheduler rather than calling every channel unconditionally.

Example:

```text
After XRoute:
    if structurally impossible → Unrelated

After shape + exact local overlap:
    if structural score cannot reach Related → Unrelated

After anchor geometry:
    if Copy certificate satisfied → Copy

After sparse geometry:
    if only Suspected is reachable → Suspected

Only if bounds overlap:
    evaluate next expensive channel

Only if ambiguity remains:
    EXACT42
```

This is the third major source of the 10× target: **not computing evidence that cannot affect the final result.**

---

# 29. API proposal

The public API remains compatible with the existing PAPH engine where practical.

```js
const q = paph.prepare(t1, t2);
const c = paph.prepare(t1b, t2b);

paph.xscreen(q, c);
paph.xcompare(q, c);
paph.xrank(q, candidates);
```

Optional modes:

```js
paph.xcompare(q, c, {
    mode: 'fast',
    fallback: true
});

paph.xrank(q, candidates, {
    mode: 'fast',
    fallback: 'defer'
});
```

Modes:

```text
fast    → accelerator-first
safe    → fast path + exact fallback
exact   → legacy/exhaustive reference
```

Default for search should be `safe` until production calibration proves that `fast` alone is sufficient.

# 31. Search engine contract

The search engine should not use PAPH-X as a replacement for retrieval.

The recommended complete system is:

```text
                  ┌──────────── exact code postings
image query ──────┼──────────── descriptor band postings
                  └──────────── external pHash / embedding if available
                               ↓
                         candidate union
                               ↓
                       PAPH-X XRank
                               ↓
                     route SIMD filtering
                               ↓
                         sparse XMatch
                               ↓
                      geometry / structure
                               ↓
                      fallback if deferred
```

PAPH remains the final copy detector; other retrieval modalities can continue nominating candidates.

# 32. Why this should exceed 10×

The performance target is based on removing work, not assuming faster instructions.

## 32.1 Screen

Current screen class:

```text
2 × full descriptor matrix
+ best/second arrays
+ correspondence construction
+ sorting
```

PAPH-X screen:

```text
route SIMD
+ small bucket probes
+ bounded support counter
```

The asymptotic change is more important than the constant factor.

## 32.2 Descriptor matching

Current:

```text
O(N²) = 262,144 descriptor pairs
```

PAPH-X:

```text
O(N·P + N·K)
```

where:

```text
N ≤ 512
P = 24 projection probes
K = touched descriptor candidates, intended to be tens rather than hundreds
```

Even before SIMD, this is an order-of-magnitude reduction in the number of full Hamming calculations on normal data.

## 32.3 Geometry

Current geometry receives a large correspondence pool that was generated for every candidate.

PAPH-X only invokes it after the route stage and feeds it a sparse, higher-quality pool.

## 32.4 Structural evidence

Current lean comparison still evaluates substantial evidence for every survivor.

PAPH-X evaluates channels until the lattice becomes decidable.

The combined effect is expected to exceed 10× on search workloads where unrelated candidates dominate, which is the normal operating condition of a large moderation/search index.


because it directly tests whether the architecture removed the quadratic bottleneck.

# 34. Required performance acceptance tests

A PAPH-X release candidate must satisfy all of the following on the reference machine:

```text
1. XRoute screen is ≥10× faster than 4.2 screen at p50.
2. XRoute screen is ≥5× faster at p95.
3. XCompare unrelated is ≥10× faster at p50.
4. XCompare copy is ≥10× faster at p50 OR the aggregate search benchmark is ≥10× faster.
5. XRank 100-candidate benchmark is ≥10× faster end-to-end.
6. Heap allocation in XScreen hot path = 0.
7. Full descriptor-pair evaluations are reduced by ≥90% on the benchmark corpus.
8. Fallback rate is reported and remains within the calibrated budget.
```

The aggregate 10× gate is mandatory even if one individual positive-copy case is slower.

# 36. Equivalence discipline

PAPH-X needs two distinct test layers.

## 36.1 Exact accelerator equivalence

Pure implementation transformations must preserve an exact reference:

```text
projection output
bucket construction
sparse candidate set
Hamming distances
best/second-best values
```

where the sparse algorithm is supposed to be equivalent for a given candidate universe.

## 36.2 Semantic comparator equivalence

Where XMatch intentionally changes the search path or evidence scheduling, test semantic equivalence against the calibrated PAPH 4.2 corpus rather than demanding identical internal vectors.

The final verdict and required report fields must remain stable within the declared calibration contract.

---

# 37. Attack resistance

PAPH-X must explicitly test attacks that exploit the accelerator instead of the image detector.

## 37.1 Bucket flooding

An attacker could attempt to generate descriptors with common projection values.

Countermeasures:

- hot-bucket caps;
- multiple independent projections;
- support thresholds;
- route entropy checks;
- fallback when the sparse candidate set explodes.

## 37.2 Repeated textures

A wall of repeated tiles can generate many descriptors with the same local pattern.

Countermeasures:

- diversity-aware anchors;
- spatial coverage;
- unique-keypoint support;
- model topology;
- repetition guard inherited from 4.2.

## 37.3 Descriptor poisoning

If a corrupted or malicious Tier-2 contains many artificial keypoints, the matcher must not allocate unbounded work.

All work remains bounded by the hard 512-keypoint contract.

---

# 38. Failure behaviour

PAPH-X must fail conservatively.

```text
invalid route profile          → Indeterminate / profile error
bad sidecar                    → regenerate / ignore sidecar
missing XBucket index          → rebuild in prepare
sparse explosion               → fallback exact
weak route + ambiguous match  → fallback or Indeterminate
unsupported profile            → ProfileUnsupported
```

No malformed accelerator structure is allowed to turn into `Unrelated`.

# 41. What should NOT be done

PAPH-X should explicitly reject several tempting but inferior directions.

## 41.1 Do not simply increase SIMD width

AVX2/AVX-512 or WASM SIMD can reduce constants, but it does not remove the 262,144-pair structure.

## 41.2 Do not keep a full N×M Hamming matrix

The matrix is unnecessary for best/second-best matching and is cache-unfriendly.

## 41.3 Do not run the screen through the full comparator

A screen is not a report.

## 41.4 Do not compute direct and mirror independently

Mirror is a descriptor permutation and a coordinate transform.

## 41.5 Do not allocate per correspondence

All hot buffers must be reusable.

## 41.6 Do not make fuzzy logic part of the exact index

The index should nominate. XRoute/XMatch should decide.

## 41.7 Do not claim 10× until the workload benchmark proves it

The target is architectural; the release number must be measured.

# 42. Reference complexity

Let:

```text
N = keypoints per side, N ≤ 512
P = number of LSH projections, P = 24
K = average touched candidate keypoints per query descriptor
A = anchor count, initially 96
C = number of route survivors
```

PAPH 4.2 descriptor matching:

```text
O(N²)
```

PAPH-X sparse descriptor matching:

```text
O(N·P + N·K)
```

Initial geometry:

```text
O(A·P + A·K + Hough(A))
```

Adaptive expansion:

```text
96 → 160 → 256 → 512
```

only when required.

Batch screening:

```text
O(Ncandidates × route_size / SIMD_width)
```

rather than one high-overhead pair invocation per candidate.

# 45. Success criterion

PAPH-X is successful only when it demonstrates the following simultaneously:

```text
               ┌──────────────────────┐
               │  ≥10× search speedup │
               └──────────┬───────────┘
                          │
              ┌───────────┴───────────┐
              │                       │
      ≥90% fewer full           no meaningful copy-
      descriptor comparisons    recall regression
              │                       │
              └───────────┬───────────┘
                          │
                  calibrated safety
                          │
                    PAPH-X release
```

The central idea is simple:

> **PAPH 4.2 made the quadratic matcher very fast. PAPH-X should make the quadratic matcher rare.**

That is the architectural change capable of producing the requested 10× improvement.

# Appendix B — the key architectural invariant

Every optimization in PAPH-X should be evaluated against one question:

```text
Does it reduce the number of expensive evidence-producing operations?
```

Reducing the cost of one Hamming operation from 2.6 ns to 1.8 ns is useful.

Reducing 262,144 operations to 15,000 is transformative.

Reducing those 15,000 to only the 96 anchor descriptors needed for an obvious model is better still.

And eliminating the entire comparator call for 90% of search candidates is the difference between a fast comparator and a scalable copy-detection system.

**PAPH-X is therefore a cascade, not a faster loop.**
